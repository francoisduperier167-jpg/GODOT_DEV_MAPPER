Tu es un architecte logiciel senior spécialisé dans Godot Engine, tooling développeur, debugging, visualisation nodale, analyse statique, runtime tracing, UX d’outils techniques, profiling, architecture logicielle, systèmes événementiels et outils d’aide à la compréhension de code.

Ta mission n’est PAS de coder immédiatement le plugin.

Ta mission est de **concevoir le plan complet, réaliste, progressif et techniquement crédible d’un projet de plugin Godot**, en structurant correctement les objectifs, les couches fonctionnelles, les modèles de données, les vues, les contraintes techniques, les priorités et la feuille de route.

Le projet doit être pensé comme un véritable outil de développement destiné à comprendre un projet Godot dans sa globalité.

---

# 1. INTENTION CENTRALE DU PROJET

Je veux créer un outil permettant de construire et explorer une **carte visuelle complète d’un programme Godot**.

Cette carte doit relier :

- l’architecture du projet ;
- les scènes ;
- les scripts ;
- les classes ;
- les fonctions ;
- les appels entre fonctions ;
- les appels entre scripts ;
- les signaux ;
- les ressources ;
- les paramètres ;
- les états ;
- les décisions ;
- les embranchements logiques ;
- les événements ;
- la temporalité ;
- les threads ou execution lanes ;
- les instances runtime ;
- les performances ;
- les événements réellement exécutés.

Le plugin ne doit PAS être un remplacement du code par de la programmation visuelle.

Ce n’est PAS un clone de Blueprints.

Ce n’est PAS un système permettant de programmer entièrement le jeu avec des nodes.

C’est un **outil de cartographie, compréhension, inspection, traçage, debugging et analyse du code existant**.

L’objectif principal est :

**comprendre comment le jeu fonctionne, étape par étape, depuis la structure globale du programme jusqu’aux fonctions et décisions internes qui produisent le comportement réel du jeu.**

---

# 2. PRINCIPE ARCHITECTURAL CENTRAL

Le projet doit être pensé autour d’une idée fondamentale :

**le modèle complet du programme existe indépendamment de la vue affichée.**

Il faut donc distinguer :

COMPLETE PROGRAM MODEL

et

CURRENT VISUAL VIEW.

Le modèle peut contenir :

- des centaines de scripts ;
- des milliers de fonctions ;
- des milliers de relations.

Mais l’interface ne doit afficher que le niveau de détail nécessaire selon le zoom, le système sélectionné, le contexte ou le mode d’analyse.

Analogie :

une carte géographique possède toutes les informations d’un territoire, mais n’affiche pas chaque rue lorsque l’utilisateur regarde le pays entier.

Le plugin doit fonctionner selon le même principe.

## C. GAME FLOW

Répond à :

« Comment le jeu se déroule dans le temps ? »

Le jeu doit être modélisé comme une succession et une hiérarchie d’événements temporels.

Exemples :

GAME

→ Main Menu

→ Level 1

→ Level 2

→ Level 3

→ Final Boss

→ Victory

→ Credits

Mais un niveau lui-même est un bloc temporel.

Exemple :

LEVEL 1

→ initialization

→ exploration

→ encounter 01

→ encounter 02

→ boss

→ level complete

Et un encounter est lui-même un bloc temporel.

Exemple :

Encounter

→ player enters zone

→ doors close

→ enemies spawn

→ combat

→ enemies defeated

→ loot

→ doors open

Et une attaque ennemie est elle-même un flux temporel.

Exemple :

TargetDetection

→ Decision

→ Chase

→ Attack

→ Animation

→ Hitbox

→ Collision

→ Damage

Le projet doit donc gérer des **blocs temporels imbriqués**.

## D. RUNTIME EXECUTION

Répond à :

« Qu’est-ce qui s’est réellement produit pendant cette exécution ? »

Exemples :

- telle branche a été empruntée ;
- telle condition a retourné FALSE ;
- telle instance a exécuté telle fonction ;
- telle valeur runtime était 5.4 ;
- telle fonction a duré 350 µs ;
- tel thread était actif ;
- tel événement a eu lieu à tel moment.

Le runtime doit être superposé à la carte structurelle existante.

# 4. VISION TEMPORELLE DU JEU

La temporalité est une composante fondamentale du projet.

Un niveau n’est pas seulement une scène.

C’est un événement ou bloc temporel qui :

- possède un début ;
- possède une durée ;
- contient d’autres événements ;
- se situe après certains événements ;
- se situe avant d’autres événements ;
- peut être interrompu ;
- peut être terminé ;
- peut échouer ;
- peut être abandonné.

Exemple :

GAME START

→ MENU

→ LEVEL 1

→ LEVEL 2

→ BOSS

→ VICTORY

Mais LEVEL 1 peut être interrompu par :

PAUSE

→ RESUME

ou :

QUIT

→ GAME END

ou :

DEATH

→ RETRY

ou :

LEVEL COMPLETE

→ LEVEL 2.

Prévoir donc un lifecycle temporel pouvant contenir des états comme :

NOT_STARTED

ACTIVE

PAUSED

COMPLETED

FAILED

ABORTED.

- multithreading ;

Probabilité

Mitigation

# 50. EXIGENCE FINALE

Ne réduis jamais le projet à un simple debugger.

Ne réduis jamais le projet à un simple graph viewer.

Ne réduis jamais le projet à une simple timeline.

Ne réduis jamais le projet à un simple outil d’IA.

Le projet est avant tout :

**une représentation navigable et multi-échelle de l’architecture, de la logique, des données, du déroulement temporel et de l’exécution réelle d’un programme Godot.**

Le runtime debugging, le tuning, le profiling et l’assistance IA sont des usages de cette carte intégrale.

La question directrice doit rester :

**Comment représenter suffisamment bien le programme pour permettre de comprendre ce qui existe, comment cela fonctionne, dans quel ordre cela se produit, pourquoi cela se produit et où intervenir pour le modifier ?**

À partir de cette question, construis maintenant le plan directeur du projet.
